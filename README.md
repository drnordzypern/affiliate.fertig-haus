# Fertig Haus Partner Portal — Frontend

The public, Partner-facing frontend for the future Fertig Haus Partner
Portal, intended for `https://affiliate.fertig-haus.net`. This repository
is the frontend/BFF side of the architecture; `saleschain-os` remains the
backend source of truth for Partner data, referrals, commissions,
authentication, and compliance.

## Current preview scope

This is a **frontend foundation**, not a full production system, with one
real, functional slice: invitation acceptance and Partner-session
login/logout, mediated entirely through this app's own same-origin BFF.
Concretely:

- All pages render real, professional German copy and a finished visual
  design — nothing here is a wireframe.
- The invitation-acceptance flow (`/einladung#token=...`) and its
  two BFF routes (`app/api/partner-invitations/accept`,
  `app/api/partner-sessions/logout`) are real and call SalesChain's
  approved public invitation/Partner-session endpoints server-to-server.
- `/portal` is a real, protected Partner dashboard: it validates the
  session server-to-server against SalesChain's `GET
  /v1/partner-sessions/me` before rendering anything, and redirects to
  `/einladung` on any non-`AUTHENTICATED` outcome (Jira `DNL1-63`). A
  well-formed cookie is never, by itself, treated as authorization — see
  "Security boundaries" below and `docs/architecture.md`, "Protected
  Partner dashboard".
- The Partner application form (`/partner-werden`) remains a
  **non-functional preview**, clearly labelled as such in the UI.
- The entire site is configured to not be indexed, cached, or previewed
  by search engines, AI crawlers, or social-preview bots
  (`app/robots.ts`, `robots` metadata on every page, and an
  `X-Robots-Tag` header on every route — see "Security boundaries").

See [`docs/architecture.md`](docs/architecture.md) for the full
architecture boundary and the security rules this integration follows.

## Architecture

```text
Browser
→ affiliate.fertig-haus same-origin BFF
→ SalesChain public/API boundary
→ SalesChain database and business logic  (source of truth)
```

This repository owns the browser-facing UI and the same-origin BFF routes
that mediate calls to SalesChain. It does not and will not own Partner
business logic, persistence, or SalesChain tokens on the client.

## Local setup

Requires Node.js **24+** (a currently maintained Node release — Node 20
reached end-of-maintenance and is not supported) and npm.

```bash
npm install
npm run dev
```

The app runs at `http://localhost:3000`.

## Security boundaries

- SalesChain is the sole source of truth for Partner applications,
  invitations, referrals, leads, commissions, verification, and
  audit/compliance. This repository implements only the narrow,
  already-approved invitation-acceptance and Partner-session boundary —
  see [`docs/architecture.md`](docs/architecture.md).
- No database, cache, or persistence layer belongs in this repository.
  The one exception is the browser's own HttpOnly Partner-session cookie.
- The browser only ever talks to this app's own origin. The same-origin
  BFF (`app/api/partner-invitations/accept`,
  `app/api/partner-sessions/logout`) is the only thing allowed to call
  SalesChain.
- Server-only configuration (see `.env.example`) is never exposed to the
  browser, logged, or embedded in a `NEXT_PUBLIC_*` variable.
- Invitation tokens travel only in URL fragments, never query strings,
  and are never logged, sent to analytics, or persisted in browser
  storage. The bootstrap token and the Partner session token never reach
  browser JavaScript at all.
- **Cookie presence is not proof of a live SalesChain session, and is
  never treated as authorization on its own.** `/portal` forwards the
  cookie server-to-server as a bearer token to SalesChain's
  `GET /v1/partner-sessions/me` on every request and only renders the
  dashboard on a strict `{status:"AUTHENTICATED"}` response — every other
  outcome (missing/malformed cookie, upstream rejection, malformed
  response, timeout, network error) redirects to `/einladung` (Jira
  `DNL1-63`; see "Protected Partner dashboard" in
  [`docs/architecture.md`](docs/architecture.md)).
- **Both BFF routes reject cross-origin requests.**
  [`lib/security/same-origin.ts`](lib/security/same-origin.ts) compares
  the `Origin` header against the request's own URL origin and fails
  closed on a mismatch or missing header, before any cookie read or
  SalesChain call. See "CSRF / same-origin protection" in
  [`docs/architecture.md`](docs/architecture.md).
- **Private responses are never cached or indexed.** `X-Robots-Tag:
  noindex, nofollow, noarchive, nosnippet, noimageindex` applies to every
  route (`next.config.ts`), `Cache-Control: private, no-store` applies to
  `/portal` and both BFF routes, and `robots.txt` disallows all crawling.
  See "DNL1-63: route classification and adversarial verification" in
  [`docs/architecture.md`](docs/architecture.md).
- **Logout and `/me` share the same guard, but only `/me` is
  non-destructive.** `POST /v1/partner-sessions/logout` revokes the
  session; `GET /v1/partner-sessions/me` only checks it. This app never
  uses the destructive route to validate a session, and never uses the
  non-destructive route to log one out.

Full detail: [`docs/architecture.md`](docs/architecture.md).

## What is intentionally not implemented

- A working Partner application submission
- A real referral link or QR code — SalesChain's session-validation
  endpoint deliberately returns no referral/profile data, and no other
  endpoint provides it yet (see `docs/architecture.md`, "Known
  limitation: no referral/QR data source")
- Lead tracking or commission calculation
- Analytics, tracking pixels, or a cookie banner (none are needed — no
  tracking exists yet)
- A sitemap (would claim indexable, finished routes; none exist yet)
- Final, legally reviewed Impressum/Datenschutz copy or links

   [`lib/legal-config.ts`](lib/legal-config.ts).
5. Re-enable indexing (`app/robots.ts`, `robots` metadata in
   `app/layout.tsx`) and add a sitemap once the portal is approved for
   launch.

This project is a frontend foundation and is **not** production ready —
only the invitation-acceptance/Partner-session slice and the protected,
data-sparse `/portal` dashboard described above are real.
